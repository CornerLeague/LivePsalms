# Hebrew/Greek Interlinear in the Study Context Tab

**Date:** 2026-06-25
**Status:** Design approved (pending spec review)
**Branch:** `feat/study-interlinear`

## Goal

In the Notepad **Study** section, add a dropdown/disclosure to the **Context** tab that shows the word-by-word Hebrew/Greek interlinear (with Strong's numbers and definitions) of the **verse currently selected** in the study reader. Reference for the kind of content shown: the Strong's-based lexicon at biblestudytools.com/lexicons.

## Background — current state of the codebase

Established by exploration on 2026-06-25:

- **Study area** lives in `src/notepad/study/`. Entry point `StudyWorkspace.tsx` branches into desktop (three columns: `ApparatusRail` left / `StudyReader` center / `StudySidePanel` right) and `mobile/MobileStudyWorkspace.tsx` (bottom tabs `reader` / `study` / `context`).
- **The "Context" tab is `ApparatusRail`** (`src/notepad/study/panes/ApparatusRail.tsx`), signature `ApparatusRail({ book, chapter })`. It renders **book-level** apparatus (author, date, region, genre, summary) plus a cross-references section. It uses **inline styles + CSS variables** (`--deep-umber`, `--silica`, `--lamplight-accent`, …), **not Tailwind**, and currently has no disclosure/accordion.
- **Bible text** is rendered by `BibleReader` (`src/notepad/bible/BibleReader.tsx`) via the thin `StudyReader` wrapper. Verse model: `interface ReaderVerse { verse: number; text: string }` (`useBiblePassages.ts`). Verse refs: `interface VerseRef extends PassageRef { verse: number }` = `{ book, chapter, verse }`.
- **Verse selection in study mode is tap-only and transient.** `BibleReader` holds `const [selectedVerse, setSelectedVerse] = useState<number|null>(null)` locally. `StudyReader` does **not** pass `onSelectVerse`, so the selected verse never leaves the reader and the Context tab cannot see it. `BibleReader` already supports an `onSelectVerse?.({book,chapter,verse})` callback prop — it's simply not wired in study mode.
- **There is no Hebrew/Greek/Strong's data anywhere** — no tables, no lexicon, no interlinear, no edge function. The only original-language content today is hedged prose generated by the AI study chat; its prompt states *"Phase 1: there is no structured lexicon yet."*
- **Bible data backend:** verses are in `bible_passages`, keyed by an OSIS-style id `book.chapter.verse` (e.g. `jhn.3.16`), book codes lowercase OSIS (`gen`, `jhn`, `1sa`). Reference tables `bible_books` (PK `book`) and `bible_cross_references` are **public-read** (RLS `select using (true)`) and queried directly from the client. Latest migration is `040_*.sql`; convention is zero-padded `NNN_snake_case.sql`. Apply via `supabase db push`.
- **Existing read pattern:** `useBiblePassages.ts` queries `supabase.from('bible_passages').select(...)` directly from the client — no edge function for plain reads.

## Decisions (from brainstorming)

1. **Data source:** ingest a license-clean dataset (not LLM-generated, not runtime-proxied).
2. **Display:** word-by-word interlinear — original script, transliteration, Strong's number, short gloss, morphology; tap a word to expand its full Strong's definition.
3. **Selection scope:** one verse at a time (tapping another verse replaces the panel content). Verse ranges are out of scope for the MVP.
4. **Single phased spec:** data layer first, frontend second (the frontend needs the table to exist). The ingest is the riskier phase.

## Architecture

### Data fetch — direct Supabase client query (chosen)

The lexicon is public-read reference data keyed by OSIS verse id, exactly like `bible_passages` / `bible_books`. A small client hook `useVerseLexicon(verseId)` queries the interlinear table directly; `useStrongsEntry(strongs)` lazily fetches a full definition when a word is expanded. **No edge function and no manual function-deploy step.**

Rejected alternative: a `lexicon` edge function cloning `verse-search` — more moving parts and a deploy step for no benefit, since nothing is computed server-side.

### State plumbing — lift `selectedVerse` to `StudyWorkspace` (chosen)

`passage = { book, chapter }` already lives in `StudyWorkspace` / `MobileStudyWorkspace` and is prop-drilled. Add a sibling `selectedVerse: number | null`:

- Pass `onSelectVerse={(ref) => setSelectedVerse(ref.verse)}` down through `StudyReader → BibleReader` (wiring the existing, currently-unused callback).
- Pass `selectedVerse` (plus `book`/`chapter`) into `ApparatusRail`.
- Reset `selectedVerse` to `null` whenever `passage` changes (new book/chapter clears the panel).

Rejected alternative: a new React context or zustand store — overkill for one value shared across three components in the same subtree; inconsistent with how `passage` is already handled.

## Data layer

### Migration `041_bible_lexicon.sql` — two public-read tables

Both mirror the `bible_books` / `bible_cross_references` reference-table pattern: public read, no user scope, RLS `select using (true)`.

**`bible_interlinear`** — one row per original-language word of a verse:

| column | type | notes |
| --- | --- | --- |
| `verse_id` | text | OSIS id, e.g. `jhn.3.16` (translation-independent) |
| `position` | integer | word order within the verse, starting at 1 |
| `original` | text | Hebrew/Aramaic/Greek script (with vowel points/accents) |
| `transliteration` | text | romanized form |
| `strongs` | text | Strong's number, e.g. `H430`, `G2316` (nullable — some particles lack one) |
| `morph` | text | morphology / part-of-speech code or label |
| `gloss` | text | short English gloss |
| `language` | text | `hebrew` \| `aramaic` \| `greek` |

PK `(verse_id, position)`; index on `verse_id`.

**`bible_strongs`** — the dictionary, one row per Strong's number (keeps long definitions out of every word row):

| column | type | notes |
| --- | --- | --- |
| `strongs` | text | PK, e.g. `H430` |
| `lemma` | text | dictionary headword in original script |
| `transliteration` | text | |
| `pronunciation` | text | |
| `short_def` | text | one-line gloss |
| `full_def` | text | extended Strong's definition |
| `language` | text | `hebrew` \| `aramaic` \| `greek` |

### Source datasets + licensing

- **Interlinear:** STEPBible **TAHOT** (Translators Amalgamated Hebrew/Aramaic OT) + **TAGNT** (Translators Amalgamated Greek NT) — CC BY 4.0. Provide original word, transliteration, Strong's number, morphology, and gloss per verse, with OT covered by Hebrew/Aramaic and NT by Greek.
- **Definitions:** STEPBible **TBESH/TBESG** (Brief lexicons) or the public-domain OpenScriptures Strong's dictionaries for `bible_strongs`.

All sources are CC BY 4.0 or public domain. Attribution is added alongside the existing translation attributions (the project already surfaces translation attribution via `src/notepad/bible/translations.ts`).

### Ingest scripts

New `scripts/ingest-interlinear.ts` and `scripts/ingest-strongs.ts`, modeled on the existing `scripts/ingest-bsb.ts`:

- A **pure parser** maps a STEPBible TSV row → a `bible_interlinear` row (book/chapter/verse → OSIS `verse_id`; reuse the canonical↔OSIS map in `src/notepad/graph/reference-parser.ts`). The parser is unit-testable in isolation.
- Upsert in batches into Supabase using the service role, like the BSB ingest.

This is the **riskier phase**: sourcing the exact STEPBible files and confirming their column layout drives parser details, which the implementation plan will pin down.

## Frontend

### New component: `OriginalLanguagePanel`

Lives under `src/notepad/study/` (e.g. `study/lexicon/OriginalLanguagePanel.tsx`). Rendered as the **top section of `ApparatusRail`** — it's the most dynamic, verse-tied content, so it belongs above the static book apparatus. Styled with the rail's **inline-style + CSS-var** convention (hand-rolled disclosure with a chevron; no Tailwind), to stay visually consistent with the rail.

**States:**

- **Empty** (no verse selected): muted prompt — *"Tap a verse in the reader to see its Hebrew & Greek."*
- **Loading:** lightweight skeleton rows.
- **Populated:** header shows the verse ref (e.g. *John 3:16*) + a language badge (Hebrew / Greek / Aramaic). The disclosure **auto-expands on selection**. Body is a list of **word rows**, each showing: original script (large; Hebrew/Aramaic rendered with `dir="rtl"` and an appropriate font), transliteration, short gloss, a Strong's chip, and morphology. **Tapping a word row expands its full Strong's definition inline** (lazy `useStrongsEntry`).
- **Missing data:** *"Original-language data isn't available for this verse."* (covers any verse the dataset doesn't include).
- **Definition fetch error:** inline message with a retry affordance.

### New hooks

- `useVerseLexicon(verseId: string | null)` — returns `{ words, language, loading, error }`; queries `bible_interlinear` where `verse_id = verseId` ordered by `position`. Returns empty when `verseId` is `null`.
- `useStrongsEntry(strongs: string | null)` — lazily fetches one `bible_strongs` row; cached per Strong's number within the session to avoid refetching common words.

### Data flow (selection → display)

1. User taps a verse in `BibleReader` (study reader).
2. `onSelectVerse({book,chapter,verse})` bubbles to `StudyWorkspace`, which sets `selectedVerse`.
3. `ApparatusRail` receives `selectedVerse` and computes `verseId = `${book}.${chapter}.${verse}`` (lowercase OSIS book via the existing map).
4. `OriginalLanguagePanel` calls `useVerseLexicon(verseId)` and renders the word rows.
5. Expanding a word calls `useStrongsEntry(strongs)` for the full definition.

### Mobile behavior

State is lifted to `MobileStudyWorkspace`, so a verse tapped in the **reader** tab persists and appears when the user opens the **context** tab. The MVP does **not** auto-switch tabs on selection (avoids hijacking the reader). A small "Hebrew & Greek ready" hint is a possible later addition, not part of the MVP.

## Testing

- **`useVerseLexicon`** (mocked Supabase): returns words ordered by `position`; empty array when `verseId` is `null`; surfaces error state.
- **`OriginalLanguagePanel`** (component): renders word rows; Hebrew rows use `dir="rtl"`; expanding a row reveals the full definition; empty / loading / missing-data / error states render correctly.
- **Ingest parser** (pure unit test): STEPBible TSV row → `bible_interlinear` row, including correct OSIS `verse_id` construction across OT (Hebrew/Aramaic) and NT (Greek) samples.

Follow existing vitest conventions; a collapsible-panel test precedent exists at `src/notepad/components/lamplight/ConnectionCardsPanel.collapsible.test.tsx`.

## Scope boundaries (out of scope for MVP — YAGNI)

- Verse ranges / multi-verse selection.
- Word-level search, tapping a word to navigate to other occurrences, or cross-linking to concordance.
- Audio pronunciation.
- Persisting the selected verse across sessions.
- **Any AI/LLM involvement** — this panel is authoritative dataset content only, never model-generated. Consistent with the Lamplight voice principle (artifacts never speak prophetically): a lexicon is fact, not interpretation.

## Risks / open items for the plan

- **Dataset sourcing (primary risk):** confirming the exact STEPBible TAHOT/TAGNT + TBESH/TBESG file formats and column layouts; the parser depends on them. Verify license/attribution requirements are met.
- **Coverage gaps:** the panel must degrade gracefully (missing-data state) for any verse not present in the dataset.
- **OSIS book-code alignment:** ingest must produce `verse_id` book codes that match `bible_passages` exactly (lowercase OSIS) so selection maps cleanly.
- **Deploy steps:** migration `041` applies via `supabase db push`; the ingest runs as a one-off script against Supabase (service role). No edge-function deploy needed.
