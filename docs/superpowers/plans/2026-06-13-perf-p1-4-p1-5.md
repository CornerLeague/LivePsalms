## P1-5 — Drop `animejs`  ·  effort: S  ·  risk: low

**Problem.** Three animation libraries shipped together: framer-motion `^12.38.0`, gsap `^3.14.2`, animejs `^4.4.1`.
`animejs` had **exactly ONE usage in the entire `src` tree**: a single card-entrance tween in the onboarding
`SpotlightTour`. gsap is the workhorse (~14 files); framer-motion is moderate (~6 files). The lone animejs tween is
trivially reimplementable in gsap (already a dependency) or plain CSS, letting `animejs` be dropped from
`package.json` entirely. **Do NOT touch framer-motion or gsap — both are load-bearing.**

**Site (exact import + call site).**

| File | Line (pre-fix) | Current code / issue |
|---|---|---|
| `package.json` | 52 | `"animejs": "^4.4.1",` — declared but used in only ONE source file. No `@types/animejs` (v4 ships its own types). |
| `src/notepad/onboarding/tour/SpotlightTour.tsx` | 2 | `import { animate } from 'animejs';` — the ONLY animejs import in `src`. |
| `src/notepad/onboarding/tour/SpotlightTour.tsx` | 86–100 | `animate(node, { opacity: [0, 1], translateY: [8, 0], duration: 280, ease: 'out(3)' });` — the ONLY usage: a card entrance on step change. Skipped under reduced motion, wrapped in try/catch, documented as optional progressive enhancement ("rendering must never depend on it"). |
| `src/components/sections/DesktopMosaic.tsx` | 2–4, 84–266 | The lone file importing BOTH gsap and framer-motion — **flag only, no change.** They animate *different* nested elements (gsap → grid container + tile wrappers; framer-motion → inner per-tile hover overlays); the transform boundary is intentional. No element is driven by both libs. |

**What it animates.** A 280 ms fade-and-slide-up (`opacity 0→1`, `translateY 8px→0`) of the onboarding tour card on
each step change. Lazy onboarding UI, NOT on the eager `/` homepage route.

**Fix (gsap reimplementation — the chosen + landed approach, Option A).** In `SpotlightTour.tsx`:
- import: `import { animate } from 'animejs';` → `import gsap from 'gsap';`
- tween: `animate(node, { opacity: [0, 1], translateY: [8, 0], duration: 280, ease: 'out(3)' });`
  → `gsap.fromTo(node, { opacity: 0, y: 8 }, { opacity: 1, y: 0, duration: 0.28, ease: 'power3.out' });`
- Keep the `reduced` early-return and the try/catch wrapper intact.

> **Easing note (load-bearing):** animejs v4 `'out(3)'` is a **power-3 ease-out**, so gsap **`'power3.out'`** is the
> faithful mapping. Do **not** use the default `power1`. (CSS alternative if ever needed: a reduced-motion-gated
> `@keyframes` with `cubic-bezier(0.215,0.61,0.355,1)` re-fired via `key={index}` — Option B in the full plan; not used.)

**package.json removal.** Remove the `"animejs": "^4.4.1",` line from `dependencies` and reinstall to drop it from the
lockfile + `node_modules`.

**Risk.** low — animejs powered one optional, reduced-motion-skipped, try/catch-wrapped card fade-in; worst case is
slightly different easing on a 280 ms onboarding entrance. No bundle-critical or homepage path touched. DesktopMosaic's
dual-lib boundary left untouched.

**Verification.**
1. **Visual smoke of THAT specific animation:** open the notepad onboarding tour with **reduced-motion OFF** and confirm
   the card fades + slides up on each step. (Under reduced-motion the effect early-returns by design — nothing to see.)
2. `SpotlightTour.test.tsx` already mocks `usePrefersReducedMotion()=>true`, so the entrance effect early-returns and the
   animation lib is never exercised — removing animejs cannot break it; the suite must stay green. animejs appears in
   ZERO test files → no mocks to clean up.
3. `grep -rn "from 'animejs'\|from \"animejs\"" src` returns **nothing**.
4. `tsc -b` exits 0 (NOT bare `tsc --noEmit` — the root tsconfig has `files:[]`).
5. **Confirm `animejs` is gone from the bundle:** `grep -rn animejs package.json package-lock.json` empty;
   `ls node_modules/animejs` → not found; no `animejs` chunk in the post-build `dist`.

**Status: DONE** (`70354b9`).

## P1-4 — Forced reflow  ·  effort: L  ·  risk: medium

**Problem.** On the `/` render path the dominant forced-reflow source is **not** a manual read-in-scroll-handler but
**GSAP ScrollTrigger itself**. ~16 ScrollTrigger instances are created across Hero (5), MidSectionMotion (2–3 incl. one
PIN), TwoPathInterlude (3 — easy to undercount), PurposeGrid (4), and DesktopMosaic (3) on first paint, ~13 with
`invalidateOnRefresh`. `ScrollTrigger.refresh()` (fired on load, on every webfont load, and on resize) synchronously
measures `getBoundingClientRect` for every trigger and, because MidSectionMotion **pins**, inserts a pin-spacer and
forces a full reflow of the document below it — the **~324 ms** culprit. The second, separately-attributable thrash
(**~130 ms**) is DesktopMosaic's Flip strip→grid morph, an explicit read→write→read inside a `useLayoutEffect` on mount.
Manual layout reads in actual scroll/rAF handlers on this path are minimal and mostly safe
(`HeaderDesktop.applyDom` is write-only; `useScrollDirection` reads only `scrollY`).

**Sites (exact file:line + current code at diagnosis).**

| File | Line | Issue (current code excerpted) |
|---|---|---|
| `MidSectionMotion.tsx` | 85–94 (pin) | Pinned ScrollTrigger (`pin: stageEl`) with `scrub:2` + `invalidateOnRefresh`. **Pinning is the single most expensive ScrollTrigger feature on load** — `refresh()` measures the trigger rect, inserts a pin-spacer, forces a synchronous reflow of the whole document below it; every subsequent refresh re-runs this. **Largest contributor to the ~324 ms reflow.** |
| `MidSectionMotion.tsx` | 145–150 | Second ScrollTrigger (`scrub:2` + `invalidateOnRefresh`) — joins the refresh batch. |

Re-runs on every filter change (keyed on `filteredProjects`). **The ~130 ms culprit.** |
| `DesktopMosaic.tsx` | 331–360 | Second `Flip.from` (filter reflow) with `absolute:true` also measures all cards via `flipStateRef.current = Flip.getState(...querySelectorAll('[data-flip-id]'))`. ### TIER 1 — the ~324 ms refresh storm (biggest win)
- **(a) Global config + defer creation out of the LCP window + ONE batched refresh.** In app bootstrap (`src/main.tsx`):
  `import { ScrollTrigger } from 'gsap/ScrollTrigger'; ScrollTrigger.config({ ignoreMobileResize: true });` (ignores the
  mobile URL-bar show/hide resize that would otherwise re-run a full `refresh()` + re-insert the MidSection pin-spacer on
  every scroll-direction change). More importantly, **gate ALL homepage ScrollTrigger creation behind a deferred/idle
  pass** so they aren't built during the LCP render-delay window (create in `requestIdleCallback` / after the first
  refresh settles), and call `ScrollTrigger.refresh()` **ONCE** after all are registered (batch) instead of letting each
  `gsap.context`/create trigger its own implicit refresh. **Must include TwoPathInterlude's 3 triggers** in the batch.
- **(b) MidSectionMotion pin (85–94):** add `anticipatePin: 1` and `pinType: 'transform'`, and verify the
  700vh/500vh wrapper reserves the pin height in CSS so pin-spacer insertion doesn't reflow surrounding content.
- **(c) Trim `invalidateOnRefresh`** where geometry is viewport-relative and stable — it forces a full re-measure on
  each refresh.

  **Risk (Tier 1).** medium — deferring/batching risks mis-positioned reveals if a trigger's start/end is measured
  before fonts/images settle; `pinType:'transform'` can shift stacking/overflow of the mid-section.
  **Verification (Tier 1).** Re-trace `/` (method below); confirm ForcedReflow drops well below 625 ms; smoke the
  MidSection pin (curl-lines + bloom still render, pin engages/releases). **Smoke a non-homepage ScrollTrigger route
  (notepad-landing)** — the global `ScrollTrigger.config` affects ALL routes.
  **Effort (Tier 1).** M.

### TIER 2 — the ~130 ms DesktopMosaic morph (must land ATOMICALLY with Tier 1)
Defer the whole morph setup out of the synchronous mount `useLayoutEffect` into the existing ScrollTrigger `onEnter`
(or a `requestAnimationFrame`). The section is **below the fold on load**, so building it lazily means **zero measurement
during initial homepage load.** Collapse the read→write→read to a **single** forced reflow — one `void grid.offsetHeight`
between the two dataset writes is enough; the second is redundant because `Flip.from` re-measures the grid when it builds
the timeline. (As-built: `DesktopMosaic.tsx:248–259` writes `strip` → one `offsetHeight` → `grid`, with a comment noting
the second reflow was removed; initial mount deferred at lines 311+, filter-change reruns stay synchronous so on-screen
choreography is frame-accurate.)

  **Why atomic with Tier 1.** The deferral relies on the section being below the fold at the single batched refresh.
  Splitting them risks the strip→grid "from" state being captured at the wrong layout moment (cards jump).
  **Risk (Tier 2).** medium — if the "from" state is captured before fonts/images settle, cards jump.
  **Verification (Tier 2).** Scroll to `#projects`: strip→grid morph still plays; filter tabs still reflow
  (`data-layout` strip→grid, all cards visible); `PurposeGrid.test.tsx` stays green.
  **Effort (Tier 2).** M.

### TIER 3 — Hero + WaterRipple (follow-on commit OK)
- **HeroDesktop ringFinal:** in the responsive-sizing effect, store `ringFinal` in a ref (`ringFinalRef.current =
  sizes.ringFinal`, already computed there — no CSS-var round-trip), and at the intro-timeline build use the ref instead
  of `getComputedStyle(heroEl).getPropertyValue('--ring-final-size')`. Same value, removes one `getComputedStyle` flush
  from the pre-paint intro build. (As-built: `HeroDesktop.tsx` ref declared line 40, written 219, read 281.)
- **WaterRipple:** the per-event `getBoundingClientRect` is an **interaction-path** read (not load reflow). A naive
  rect cache **MUST invalidate on scroll/resize** — the container is page-tall and the math is viewport-relative, so a
  stale rect breaks ripple positioning after any scroll (a regression the perf trace will NOT catch).
  **As-built resolution (`f1711b7`):** the overlay is `fixed inset-0` (viewport-anchored) while its container scrolls,
  so `clientY − rect.top = clientY + scrollY` — ripples landed ~`scrollY` px below the cursor. Fixed by using **raw
  viewport coords** (`clientX`/`clientY` directly), which also removed the Tier-3 rect cache + its scroll listener
  entirely. Correct at any scroll offset; no cache to invalidate.

  **Risk (Tier 3).** low — HeroDesktop ring change is the same value with no round-trip; WaterRipple viewport-coord fix
  is identical at top-of-page and correct at any offset.
  **Verification (Tier 3).** Hero intro still renders the expanding ring (screenshot). WaterRipple: ripples appear at
  the correct cursor position **after scrolling** (validates the viewport-coord fix). `tsc -b` 0.
  **Effort (Tier 3).** S.
