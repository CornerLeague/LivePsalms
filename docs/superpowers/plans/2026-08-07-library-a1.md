# Phase A1 — broaden the grounding corpus, implementation plan

**Goal:** take the library from three 19th-century British Reformed-adjacent sources to eight spanning patristic, Catholic, Wesleyan/Methodist, Reformed and Reformation-era traditions — so that B3's *Deeper In* door has something to be deep about.

Parent design: `docs/superpowers/specs/2026-08-06-study-insights-design.md` §3.1. Runbook to extend: `docs/runbooks/library-ingest.md`.

**Sequencing decision (Myles, 2026-08-07):** A1 before B3. Door 2's value over Door 1 is breadth of interpretation, and on today's corpus it would read as Door 1 with different headings.

**Also decided, for B3 when it comes:** Door 2 **keeps** the blanket contested-passage rejection, like Door 1. It is descriptive, generated once, and served to everyone from a shared cache — the same risk posture that decided Door 1. Record this in the B3 design; do not re-litigate.

## ⚠️ Read before starting: A1 makes retrieval WORSE unless Task 1 lands first

`fetchByChapters` in `_shared/library-retrieval.ts`:

```ts
.or(chapterOrFilter(pairs))
.limit(LIBRARY_ROW_CAP)      // 500
```

**No `ORDER BY`.** And the cap truncates *before* `searchLibrary` applies `inRegister`, `overlapsRef` and `bySpecificity` — so ranking only ever sees whatever 500 rows Postgres happened to return.

Today that already bites: **Psalm 119 holds 719 rows.** The code comment claiming "a chapter's worth of commentary is a few dozen rows; the cap only bites on pathological chapters" is already false.

After A1 it bites nearly everywhere dense — Psalm 27 goes ~123 → ~740, John 1 ~43 → ~260. Because the truncation is unordered, **which sources survive becomes arbitrary, and A1 could silently drop entire traditions from exactly the chapters it exists to enrich.** That is the opposite of the goal, and it would be invisible: the door would still render, just narrower.

**So the cap is Task 1, before a single new row is ingested.**

Design §7 says "Door 1 biases `devotional`". But `registers` is a **hard filter**, not a bias, and on the real corpus that filter is destructive. Measured with a free grounding-only sweep (`2026-08-07-a1-door1-devotional` against `2026-08-07-a1-cap-after-door`):

|---|---|---|

| `passage-nahum-1` | treasury, jfb | **treasury only** |

Two voices become one on every fixture, because `devotional` is only Treasury + Matthew Henry and Treasury fills all four slots. On Nahum 1 it is worse than narrow: Treasury is **Psalms-only** and reaches Nahum through the `psa 91:1` cross-ref anchor, so filtering swaps JFB-on-Nahum for **Spurgeon-on-a-cross-referenced-psalm**.

**A1 does not fix this.** All five incoming sources are exegetical or confessional, so `devotional` stays at two members. Door 1 wants a soft bias (rank boost) or nothing at all — not this filter.

**Where steering genuinely pays off is Door 2**, which is what it was designed for: after A1, `exegetical` has five or six members, and an unsteered top-k goes to whoever has the most rows on that chapter — Clarke, at 21,051 entries, by a wide margin.

### The Geneva strip needed the real dump, not the format description

Two things only the 14,695-entry dump revealed:

1. **Markers are alphanumeric, not just letters.** `(a)` covers 14,668 entries — but Genesis 6:16 uses `(1)`. Matching `[a-z]` only would have left ~1,700 entries un-stripped, silently duplicating Scripture into the corpus.
2. **"The Argument" must survive.** 35 entries carry a book-level preface and in **28 of them it sits BEFORE the first note marker** — so a naive cut-at-first-marker would have deleted the single best summary Geneva has for those books. The cut is at whichever comes first.

Verified on the real dump: 4.4M → 3.0M chars, all 35 prefaces preserved.

## Task 7 — ✅ the statement timeout, investigated

**Answered 2026-08-07 on an idle database, after embedding finished. All three questions below now have measured answers, and the investigation found a regression I had introduced in Task 1.**

### 1. Does it reproduce on an idle database? — Mostly no, and it is two different queries

| query | verdict |
|---|---|
| the retrieval fan-out | **Healthy.** 64–216ms per source across `psa 27`, `psa 119`, `jhn 1`; zero errors. The one 1,039ms reading was a cold start, not a slow source. Timeouts appear only intermittently now. |
| `fetchUnembedded` (ingest only) | **Genuinely slow by design.** `where source_id = X and embedding is null` is a shrinking needle: as rows get embedded it scans more to find fewer. It timed out for Calvin even running alone. Handled by the resume loop — `--embed-only` is idempotent — and it is a one-off cost, not a request path. |

The five-way parallel embed was the real trigger for the original failures: three sources completed under it, two did not, and both finished on a sequential retry.

### 2. Is the query indexed? — No composite index, and it does not need one

`library_chunks` has `(book, chapter, verse_start, verse_end)` and `(source_id)` separately, nothing covering `(source_id, book, chapter)` together. Measured, that is fine: worst per-source query is 216ms on a 111,637-row table. **No migration added** — an index on measurement rather than on suspicion.

A partial index for `embedding is null` would speed the ingest path, but that path is one-off and already has a retry loop, so it is not worth a migration either.

### 3. Should `safely` swallow it? — It exposed a REGRESSION IN TASK 1, now fixed

Worse than the original concern. `fetchByChapters` used `Promise.all`, so **one source's error rejected the whole fan-out**, `searchLibrary`'s `safely()` caught it, and the **entire anchor channel returned `[]`**. One timing-out source lost all eight — strictly worse than the single query the fan-out replaced.

Now `Promise.allSettled`: a failing source costs that source only, and the failure is **logged by name** so a narrowed corpus is diagnosable. Three tests pin it, including that all-sources-failing still yields `[]` rather than pretending.

This was the real find. The grounding floors only fire at *zero* excerpts, so with eight sources a silently dropped tradition is indistinguishable from a normal result — the same invisible-shortfall shape as #114.

### Also re-measured

The Door 1 devotional question was re-run under the degradation, so its numbers were directional. On the clean run the conclusion is unchanged: unfiltered gives `treasury, jfb` / `clarke, calvin, wesley` / `treasury, jfb, clarke` — broader than devotional-only on every fixture. **Do not filter Door 1.**

## Task 7 — original questions (kept for the record)

**Run this once embedding finishes**, so the database is not under five concurrent write jobs.

Observed 2026-08-07 during a `--grounding-only` sweep: Postgres `57014 canceling statement due to statement timeout`, on a run that nonetheless reported **PASS** with 4 excerpts per fixture. `searchLibrary` wraps each channel in `safely(...)`, so a timed-out query returns `[]` and retrieval quietly narrows.

Three questions, in order:

- [ ] **Does it reproduce on an idle database?** If it only happens under the embedding load, it is a transient worth noting and no more. If it reproduces idle, Task 1's fan-out is marginal and needs an index or a different shape.
- [ ] **Is the query using an index?** Task 1 turned one query into **eight**, each now `.eq('source_id')` + `.or(book/chapter)` + `.order('verse_start')` against a table that just grew 34k → 112k rows. Check for an index covering `(source_id, book, chapter)`; the existing one may only cover `(book, chapter)`, which makes the per-source filter a scan.
- [ ] **Should `safely` swallow a timeout here at all?** It was written when the anchor channel was ONE query — losing it lost a whole channel, and degrading was clearly right. Now it is eight, and losing one silently **drops a single source**, which is invisible: the grounding floors only fire at *zero* excerpts. With eight sources a missing tradition looks exactly like a normal result. Consider surfacing per-source failures so the eval can fail on them.

**Also re-run then:** the Door 1 devotional measurement (`2026-08-07-a1-devotional-remeasure`) was taken during this degradation, so its numbers are directional rather than final. The conclusion — do not filter — held on every fixture and is unlikely to flip, but it deserves a clean run.
